# 0007: Bound webhook replay with signed event timestamps

Zoho signs the URL-decoded body, including event timestamps, but does not sign the header timestamp. Header freshness alone cannot prevent replay after a receipt expires.

Retain receipts for at least 30 days, or the configured retention when larger. Freshness is per event. Skip an event whose time is missing, older than receipt retention minus one day, or more than five minutes in the future, because substituting receipt time would remove the replay bound. Apply the other events of the body, so one untimed event cannot drop a fresh bounce or complaint and its suppression. A correctly signed body with no fresh event stores a `stale_event` failed receipt, applies no event, invokes no callback and returns 200, so Zoho neither redelivers nor disables the webhook.

Read email event time only from documented fields: `event_data[].details[].time`, else `email_info.processed_time`. `event_data` and `details` may each be an object or an array. Epoch numbers below 1e12 are seconds, because read as milliseconds they would predate September 2001. A string time must be ISO 8601 with `Z` or a numeric offset; a string without a zone designator is no event time, because its instant would depend on the runtime's local zone. Undocumented fields such as `occurred_at` and `timestamp` are never read. Zoho documents no WhatsApp event-time field, so WhatsApp events never receive `occurredAt`, even when they contain email-shaped timestamp fields. WhatsApp webhooks are rejected and their delivered, read and failed transitions stay inactive until a captured live payload names one; one attended live capture qualifies webhooks. Cleanup and verification share the receipt retention calculation.

Only receipts from committed event transactions participate in provider-event-ID and body-hash deduplication. Failed receipts are indexed separately by `reason` and never block a later valid delivery. Message lookups reflect patches made by earlier events within the same transaction.
