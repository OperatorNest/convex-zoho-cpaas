# 0004: Own channel-aware retries

Enqueue workpool actions with `retry: false`. Completion schedules at most five total attempts with exponential backoff and bounded `Retry-After`. Email retries network failures, 429, 5xx, and recognized daily-limit errors unless classification forbids retry. A lost email response can cause a duplicate email; idempotency keys prevent duplicate component jobs, not duplicate provider sends.

SMS and WhatsApp retry only explicit 429 or 503 rejections carrying a code in the package’s known Zoho code lists. Unrecognized 5xx body codes cannot establish a definitive rejection. Transport failures without a response record `unknown` and are never automatically resent for those channels. A later attempt that finds an SMS or WhatsApp message still `sending` records `unknown` instead of resending it. WhatsApp delivered, read and failed events and email bounce and complaint events resolve `unknown`; email open and click events do not, and no event resolves an unknown SMS, so a new SMS send needs a new idempotency key. Completion cannot overwrite a delivery with transport uncertainty. Stuck actions also record `unknown` with `ZOHO_CPAAS_NETWORK_ERROR`. Suppressions and the effective SMS India endpoint are rechecked transactionally before every attempt.

Caught action failures before `fetch` starts are definitive `ZOHO_CPAAS_INVALID_ARGUMENT` failures; the same idempotency key can create a new send. Failures after the request may have reached Zoho remain uncertain.
